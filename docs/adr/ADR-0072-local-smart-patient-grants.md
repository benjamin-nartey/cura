# ADR-0072 — Local SMART-style patient grants

Date: 2026-11-03. Status: implemented locally; qualified/formal review pending.

P06-F02 adds scoped app authority to existing identity and purpose gates. A workspace cookie or Foundation bearer session is not a SMART access token. Existing legacy FHIR endpoints and P06-F01 internal workbench continue using their existing authorization boundary; the new resource server requires its own opaque bearer token and never falls back to a cookie.

Cold starts retain the original authorization request and use the existing login/MFA flow in a separate tab. Explicit continuation revalidates that request before any patient approval; sign-in alone grants nothing. No arbitrary post-login return URL or replacement authentication mechanism is added.

Implement the standalone public-client authorization-code pattern with mandatory PKCE S256 and explicit patient selection/approval. Only `launch/patient` and exact `patient/{type}.r` scopes for the seven current-source types are accepted. Scopes intersect the registered client maximum and the delegating workforce user's current permissions. Purpose is the existing TREATMENT context, not an app-supplied assertion. Search, wildcard/user/system scopes, clinical writes, refresh/offline access, OpenID identity tokens, EHR launch and a full SMART certification claim are outside this feature. Discovery reports the implemented subset.

Schema 49 is additive. Clients are organization-owned and registration retries bind a request hash to a stable key. Pending approvals bind the original user/session/facility/purpose, registered redirect, audience, scope, PKCE challenge and a hashed approval nonce. Decisions are transactional and single-use. A 60-second hashed authorization code grants a maximum five-minute, immutable patient context. Access tokens are random and stored only as hashes. A code replay revokes its grant, including a previously issued token; the rejection is raised after committing that revocation. No token verifier or access-token plaintext is stored in clinical tables or audit. Original identity session references remain private security metadata.

Every resource request reloads the original identity session through Foundation (or the existing SQLite identity provider), checks the current account, membership/role policy, client status/version, audience, grant, patient and purpose, then uses the authoritative source getter. Scope denial precedes clinical record lookup. A post-read patient-reference check also prevents a reparenting race from widening the patient context. Local source-key resolution is capped at 5,000 candidate IDs per patient/type and fails explicitly beyond that bound; it does not silently return an incomplete result.

Apps receive a base-R4 projection without the proprietary source-context extension or its profile assertion. Internal source exports also exclude transport correlation metadata: historical correlations could contain session identifiers and are not clinical facts. Stored source rows are preserved. The source transform patch is 1.0.1; StructureDefinitions remain 1.0.0 because their FHIR constraints are unchanged. Earlier internal previews must be reloaded. This is a privacy correction, not a loss of patient facts or a clinical migration.

Local client origins require cookie isolation. HTTP cookies are not isolated by port. The fixed CuraSphere-owned callback on the configured issuer is permitted for the built-in simulation. Other callbacks must use a separate port in the reserved `smart-client.localhost` hostname namespace. The workspace proxy rejects that namespace on every route, including forwarded hostnames, so it cannot issue workspace cookies there. Do not host untrusted app code on the workspace origin. Redirects are revalidated on use, so older registrations do not bypass the corrected policy. CORS permits registered client origins without credentials; discovery alone is public. Token/resource endpoints ignore workspace cookies.

App authorization pages deny framing. Workspace forms use a same-origin referrer policy because `no-referrer` can yield opaque origins on native form posts; opaque origins remain rejected. The callback uses no-referrer, removes the code from its URL before exchange, validates browser-bound state, uses explicit same-origin policy for its own subsequent fetches, and keeps access tokens in memory. Only the transient PKCE/state attempt crosses the redirect in sessionStorage, and it is removed after exchange or denial. Neither token values nor patient facts are put into navigation parameters or app-use audit.

This is internal/local synthetic treatment-app delegation, not an external clinical sharing release or patient-consent/legal determination. Production, real-PHI, external-healthcare and publication configurations remain rejected by the existing sandbox gate. F03 must separately implement consented partner delivery/import/replay contracts. No production functionality or governance approval is enabled by this ADR.
