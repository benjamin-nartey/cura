# P11-F03 Durable execution

The local Temporal workflow advances an existing SQLite run by opaque ID. SQLite remains the authority for run status, tool checkpoints, and approval records. Temporal history carries no session token, chart content, or source identifiers. The worker uses a local synthetic session for one principal and can only advance that principal's runs.

The workflow uses bounded activity retries and a fixed workflow deadline. Application policy failures are terminal. Cancellation stops an active run at its next SQLite transaction boundary. A run already awaiting approval is handed off to the existing review workflow. Automatic approval and production execution remain disabled.

For local operation, start Temporal with `docker compose -p cura-p11-temporal -f infra/local/compose.yaml up -d temporal`. Use the existing local synthetic sandbox flags and point `DATABASE_PATH` at the same disposable database in both the worker and web processes. Set `CURASPHERE_AGENT_TEMPORAL=true` on the web process. Set `CURASPHERE_AGENT_SESSION_ID` on the worker to an active local SQLite session for the same synthetic identity used in the web workspace. Run `node --import tsx tools/agents/temporal.ts worker` from the repository root. Each worker dispatches only the running rows in its bound scope. Refresh the run page to inspect progress or cancel an active run from the page.

The dispatcher uses the run ID as the Temporal workflow ID and rejects duplicate starts. A transaction checks the submission receipt before creating a run. Each checkpoint commits with its corresponding SQLite effect. A lost acknowledgement can therefore replay the activity without duplicating a step or approval. The activity allows three attempts within 75 seconds, with an eight-second limit for each attempt. The Temporal workflow has a three-minute deadline. The existing manifest continues to limit when agent execution may start or resume. A worker can reconcile terminal Temporal status into the run after it reconnects with an active session.

The Temporal integration test terminated a real worker after it committed the approval checkpoint and before it acknowledged the activity. A new worker received the retry and returned the persisted state. The run kept two steps and one approval. The test also exercised duplicate submission, a pre-cancelled run, and a poison manifest that failed with zero steps.
