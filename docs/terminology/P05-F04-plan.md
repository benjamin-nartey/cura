# P05-F04 — Facility formulary and catalogs

Continuation authorizes local synthetic engineering after P05-F03 verification. Formal acceptance, clinical/licensing approval and production functionality remain ungranted. Source Phase 05 requires local drugs/procedures/tests/units/status/versioned facility overrides and archived orders retaining their original catalog version. Existing work_orders, medication primitives, legacy formularies and billing snapshots must be preserved.

Story: permitted catalog managers register immutable versions of organization-default items or active-facility overrides. Staff inspect current availability and provenance. Existing internal department requests may select a versioned test/procedure item; the request snapshots exact catalog, terminology and unit metadata in its existing transaction. Drugs are managed as administrative formulary metadata only, never prescribed, dispensed or ordered by this feature.

Risk class C conservative engineering classification: incorrect catalog selection, inactive fallback, stale override, wrong facility, semantic drift, lost concurrent update and stale picker. Schema 47 adds immutable item versions, explicit current heads, idempotent command receipts and immutable work-order pins. No clinical source rewrite or billing tariff change. Organization defaults are tenant-local, not shared across unrelated tenants. Unknown keys fail closed. An inactive, expired, future or stale facility override never falls back to a default. Overrides pin an exact current organization-default version; a changed default requires a new override before selection. New versions require expectedRevision and append history. Item kind and concept identity/category remain fixed per key; unit/status/display/provenance may be revised explicitly with immutable prior versions retained.

Metadata: drug/test/procedure, exact controlled synthetic concept, display, explicit unit code/pack version, active/inactive/retired, effective interval, provenance URL/note, base version for facility overrides, creator and digest. Restricted catalog unit pack includes the existing mathematical symbols plus local count symbol 1; it is not general UCUM conformance or dose guidance. Drug catalog entries never enter the department-request path.

Permissions: terminology.read for catalog inspection; new facility.catalog.manage for organization/facility administrators and pharmacists in their active facility. Organization-default changes also require terminology.manage (organization administrator). Active scope/account, server-derived facility and local synthetic/dependency gates apply. Global defaults are safe tenant defaults, not licensed clinical master data. UI/API cannot supply another facility or actor. Four-eyes clinical activation is not implied by administrative edits.

Services/API v1: GET/POST /api/terminology/catalogs and GET /api/terminology/catalogs/resolve?key=...; shared bounded known-field JSON, cookie workforce sessions, no-store, foreign-Origin denial, 401/403/404/409/422/503. Writes atomically append version, compare-and-swap head, receipt, audit and metadata outbox event. Idempotency binds actor and normalized payload. Historical orders read their pinned snapshot, not current heads. Existing order routing/cancellation/history and clinical gates remain intact. The old request list remains compatible; F05 will address broader picker conformance.

UX: catalog/formulary list with resolved origin, availability and blocking reason; version detail/provenance/history; permission-scoped registration with expected revision; explicit facility-vs-default scope; current test/procedure choices on existing request form and catalog provenance on request detail. Loading/empty/error/conflict/offline/retry and accessible responsive controls. Mobile uses separately authenticated web handoff. No new native clinical editor.

Tests: persistence/reopen, safe inheritance and facility isolation, stale/inactive override, optimistic/idempotent/concurrent changes, unknown/expired/reference-only/unsupported units, drug-order denial, role/tenant/suspended account, immutable heads/history/pins, preserved cancelled/closed-encounter order snapshot after catalog change, atomic order/head/outbox failures, migration failure/recovery, production/dependency denial, real browser management/order/provenance and existing full regression suites. Rollback is application access removal with retained immutable data; fixture teardown removes 47 before earlier extensions.
